## Required implementation details

1. **Bind authorization to the paired device and conversation.** The plan currently derives immutable identity from caller payload only and treats connection generation as optional. In 0623, `PeerBridge.onEnvelope` carries only an envelope; dispatch to the main actor can outlive its authenticated connection. Carry a host-derived stable paired-principal identifier plus connection generation, revalidate it when processing an envelope, and bind it to the durable request key. Never trust a device identifier sent in the request. Reconnect by the same authorized device may observe; revocation/re-pairing and stale queued connection events must not publish, cancel, or adopt old work. Phone-provided conversation IDs need a host-owned mapping or explicit permission check so they cannot select arbitrary local/browser history or attach a conflicting turn. Keep raw credentials out of the journal. Test re-pair/revoke, stale connection callbacks, and foreign conversation IDs with zero dispatch/cancellation and no result disclosure.

2. **Make persisted callbacks mechanically distinct.** In 0623 `RivuneRunCoordinator.update`, a failed `persist()` sets an in-memory failed status and still calls `publish`, which invokes `onUpdate`. Therefore an ordinary terminal callback is not proof of a saved terminal result. Add a typed persisted-update receipt or equivalent verified resolver tied to the saved revision/digest; emit remote journal completion and terminal acknowledgement only from that path. Treat local persistence faults separately. Require a real production journal URL; the coordinator's current nil-URL persist is intentionally a no-op and cannot back a durable remote route. Test failure after admission and during terminal persistence: no completed replay reference or false durable acknowledgement, no redispatch, preserved recovery status. Also make per-run revision nonnegative and reject overflow/corrupt values.

3. **Specify all terminal and cancellation races.** V4 returns `.reattach` for `.failed` and `.cancelled`, while the plan only enumerates running/stopRequested/interruptedUnknown. Failed/cancelled records do not carry a `RemoteResultReference`; define their safe terminal response explicitly. Repeated Stop, Stop racing completion, local Mac cancellation/history deletion, and Stop after an interrupted restart must each have a tested mapping. If completion wins, replay completion rather than falsely acknowledging cancellation. V4 `confirmCancelled` requires prior stopRequested; native-owned cancellation cannot skip that transition. Current coordinator `cancel` returns Void and marks cancellation without waiting for the provider operation: distinguish a persisted local cancellation decision from confirmed provider termination, retaining task/process cleanup and avoiding claims that billing or remote execution has certainly stopped. Every observer receives at most one consistent terminal outcome; no failed/cancelled/unknown case triggers another provider call.

4. **Specify a nonmutating lookup covering consumed IDs.** Plan phase 3 says to check whether the journal already knows an ID before fresh readiness checks. V4 `record(requestID:)` excludes tombstones, while `admit` reserves unknown IDs. Do not use `admit` as a read-only probe before fresh admission, and do not treat record(nil) as proof that an ID is new. Add a bounded read-only matching lookup covering both records and tombstones, or an equivalent atomic API that requires fresh admission only for truly new IDs. Test a pruned matching retry and a conflicting retry after current routes change: return expired/conflict without reservation, dispatch, or rewriting consumed identity. Keep canonical hashing deterministic across Mac/iPhone and bind all admitted identity fields, including the host-derived owner and conversation mapping.
